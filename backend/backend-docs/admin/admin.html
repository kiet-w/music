Admin Module

Module xử lý các nghiệp vụ quản trị hệ thống, cung cấp các API chuyên dụng để quản lý bài hát và dọn dẹp các tệp tin lưu trữ.

1. Tổng quan Kiến trúc (Component Overview)

Mục đích của việc tách biệt layer là để đảm bảo Separation of Concerns (Controller mỏng, Service xử lý nghiệp vụ) và Modularity (tránh trộn lẫn logic xóa quản trị vào SongsModule hay StorageModule).

2. Dependencies & Injection

Dependency Vai trò / Chức năng
SongsModule Được import vào AdminModule để chia sẻ provider liên quan đến Song.
StorageModule Được import vào AdminModule để chia sẻ provider xử lý tệp tin.
SongRepository Giao tiếp trực tiếp với DB thực hiện các câu truy vấn quản trị (VD: xóa bài hát).
StorageCleanupService Xử lý logic tương tác với hệ thống lưu trữ object/file (xóa file rác/hỏng).

Lưu ý: Tái sử dụng Service qua Module Imports giúp tránh Code Duplicate, không phải viết lại cấu hình hoặc import ngoài luồng Nest DI.

3. Entry Points & Data Flow

DELETE /admin/tracks/:id

DELETE /admin/tracks/:id

Xóa một bài hát cụ thể dựa trên định danh id.

Chi tiết xử lý:

  • Input: Tham số id trích xuất từ URL.
  • Logic: Gọi trực tiếp songRepository.delete({ where: { id } }).
  • Trạng thái HTTP trả về: Hiện tại đang trả về 200 OK (Khuyến nghị sửa thành 204 No Content).
  • Lỗi có thể xảy ra: [404] Prisma RecordNotFound nếu id không tồn tại.

POST /admin/storage/cleanup

@HttpCode(HttpStatus.OK) POST /admin/storage/cleanup

Yêu cầu dịch vụ lưu trữ xóa tệp trên bucket tương ứng (dọn dẹp Storage).

Chi tiết xử lý:

  • Input (DTO): CleanupStorageDto gồm bucketName (string) và path (string).
  • Validation: DTO được áp dụng @IsString() và @IsNotEmpty().
  • Logic: Gọi StorageCleanupService.cleanupFile(dto.bucketName, dto.path).
  • Output: { message: 'Storage cleanup initiated', file: dto.path }
  • Lỗi: [400] BadRequest (thiếu body params) hoặc [500] InternalServerError (xóa lỗi).

4. Đánh giá & Cải thiện (Evaluations)

✅ Điểm Tốt

  • Layer rõ ràng: Controller mỏng, Service rõ ràng. Controller chỉ parse request và trả về response.
  • Validation mạnh: Sử dụng class-validator thông qua DTO chặt chẽ.
  • Tái sử dụng cao: Kế thừa hiệu quả SongRepository và StorageCleanupService từ module khác qua hệ thống Dependency Injection.

❌ Cần Cải thiện (Tech Debt)

1. Thiếu Guard / Bảo mật phân quyền

Các endpoint Admin đang hoàn toàn public. Bắt buộc phải áp dụng Guards.

// Sửa đổi đề xuất:
@Controller('admin')
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles(Role.ADMIN)
export class AdminController {}

2. Xử lý lỗi (Error Handling) thiếu an toàn

Phương thức deleteTrack chưa kiểm tra sự tồn tại của entity trước khi thao tác, dễ ném Prisma Error thuần ra ngoài HTTP Response.

// Sửa đổi đề xuất:
async deleteTrack(id: string) {
  try {
    return await this.songRepository.delete({ where: { id } });
  } catch (error) {
    throw new NotFoundException(`Track with id ${id} not found`);
  }
}

5. Hướng dẫn Debugging

Lỗi Prisma/Repository khi xóa bài hát:

  1. Đảm bảo ID truyền vào tồn tại. Chạy lệnh npx prisma studio để kiểm chứng dữ liệu.
  2. Kiểm tra các Foreign Key constraint (khóa ngoại) bị vướng: ví dụ bài hát đang nằm trong Playlist hoặc Likes.

Lỗi Xóa File trên Storage:

  1. Kiểm tra bucketName và path truyền vào có chính xác không.
  2. Xác minh biến môi trường kết nối đến Storage (VD: AWS S3 credentials, GCP JSON, STORAGE_BUCKET) còn hiệu lực.
  3. Mở log server kiểm tra stack trace từ StorageCleanupService.

6. Biến môi trường (Environment Variables)

Module không trực tiếp đọc biến môi trường, mà phụ thuộc vào cấu hình của các module cung cấp:

DATABASE_URL=          # Kết nối Database cho SongRepository
STORAGE_BUCKET=        # Cấu hình Default Bucket cho StorageCleanupService
